01 · Product promise

A memory you can act on.

The main daily job is remembering tasks and appointments. The lasting value is knowing what happened, what you bought, and what you still want to do with it.

Plan today

“Call Mum tomorrow. Dentist on Friday at ten.”

A task with a due date, plus a timed calendar event.

Remember the day

“Went to the gym and had lunch with May.”

A source record now; a daily summary and activity tags later.

Know your things

“Bought Naruto volume 1. I want volume 2.”

An owned book, a purchase, and a wishlist item.

In the first version

  • Connected voice recording and editable transcript.
  • Selected cards saved to tasks, calendar, Library, and purchases.
  • Configurable Library collections and searchable dated history.
  • Daily summary, editable activity tags, and spending totals.

Later

  • Text-only capture and offline recording.
  • Notifications and external calendar export or sync.
  • Spending limits and nutrition estimates.
  • Formulas, rollups, and arbitrary database views.

One recording → several cards

“I went to the gym, bought Naruto volume 1 for 150 baht, and need to call Mum tomorrow.”

  • Text: the reviewed source record.
  • Purchase: Naruto volume 1 · ฿150 · Book.
  • Task: Call Mum · tomorrow.

Gym becomes an activity tag when the day is summarized. Buying the book does not mean it was read.

Save means save

  • Review dates, titles, and extracted details at a glance.
  • Deselect unwanted suggestions. Finish in one action.
  • Missing optional details do not block a purchase.
  • Complete details from Home or the saved card’s menu.
  • Keep the reviewed source text even when all extracted cards are deselected.

Design proposal: the source-text card is always kept; selection applies to extracted results.

Recording failure is a hard stop

If the server is unavailable, recording cannot begin. A failure during recording stops capture and shows an error. No partial transcript, audio draft, or offline queue is retained. The user can start again after the connection recovers.

“Have I bought this issue?”

Search Naruto volume 1 in Items. Open its ownership and purchase history. A second purchase links to the same item rather than hiding the duplicate transaction.

“Which books have I not read?”

Open Book. Filter Reading status = Unread. This is a field query, not a manually maintained unread tag.

“Things I want”

“I want Naruto volume 2” creates a wishlist item. A later purchase links to that item, changes ownership, and creates the expense.

“What did I buy last year?”

Search purchase history with a purchase-date range. Relative periods are calculated when searching; “last year” is not a permanent tag.

Try it: junk food this week

This sample searches dated history. Repeated meals are separate records, so the count answers “how many recorded occasions?” rather than “how many distinct dishes?”

0matching records

Demo “this week”: 19–25 October 2026, Monday–Sunday, Asia/Bangkok. Dates and classification are sample data; Junk food is a personal label.

Count records, not joined tags

A matching history record counts once even if several tags or linked fields match. Search should preserve visible filters and show a useful empty state. A meal without a purchase can exist as consumption history; a purchase-date filter naturally excludes records with no purchase date.

05 · Flexible, with useful structure

A “big tag” defines its own fields.

In the interface, Book can feel like a tag that opens a table. In this plan, collection names that configurable table so it stays distinct from a value such as Manga or an activity tag such as Gym. The final interface wording remains adjustable.

Book · example configuration

FieldTypeDefault

Supported field types

  • Text: notes, author names.
  • Number: volume, quantity.
  • Date: finished reading on.
  • Checkbox: a simple yes/no value.
  • Single select: reading status.
  • Multi-select: genres, food classifications.
  • Item link: another Library item.

No formulas or rollups in this version. Typed defaults must match their field type.

Activity tags

Gym · Reading · Chiangmai trip 2026

Describe days and experiences. They can span days and are editable independently of generated summary text.

Library classification

Book collection · Category = Non-fiction · Reading status = Unread

Organizes items and their attributes. Purchases retain one primary spending category and one optional subgroup; flexible Library labels are additional, not duplicated expenses.

Tag creation and selection

  1. Reuse: prefer an existing matching tag or collection and its allowed field values.
  2. Suggest: the LLM may suggest a new tag when nothing fits. Keep suggestions distinguishable from accepted structure.
  3. Explicit command: “Next week I will go to Chiangmai. Add new tag Chiangmai 2060.” Produce a selected tag-creation card using that exact name; saving accepts the instruction. Do not silently change 2060.
  4. Apply with evidence: subsequent relevant records can use that tag. A plan can link to the trip, but an activity summary must distinguish planned travel from completed travel.
  5. Connect contexts: explicitly link the activity tag to Library items or history records so the trip page can show days, purchases, and related things.
Proposed default behavior

Apply collection defaults when creating a new item or on its first qualifying purchase. Explicit speech such as “I already finished it” wins over a default. Buying an existing finished book again must not reset it to Unread. Changing a default affects future records; it does not overwrite old values.

The tag-creation card is a design proposal for fitting explicit commands into the agreed select-and-save flow. Full automatic schema creation is not implied. Configure custom fields outside capture.

Proposed implementation: versioned background jobs

The server owns the schedule. Saving a record increments the day’s revision and queues a job where needed. Combine rapid saves into one latest-input job; publish only a result matching the current source revision. Keep the previous summary if generation fails and allow retry. A failed summary must never undo a saved purchase or task.

Correction rule: keep user-added and user-removed activity-tag overrides separate from generated associations. This stops regeneration from putting an explicitly removed tag back.

08 · Proposed Supabase design

Flexible tables in the app.
Stable tables underneath.

This is a proposed logical model, not a migration. A user-created Book collection adds metadata and typed values rather than requiring a new physical SQL table for every tag. It gives the Notion-like table experience while keeping links, permissions, and search consistent.

Journal sources

Original transcript, editable current text, journal date, recording timestamp.

Daily journals

One summary per user/day, input revision, generation state.

Activity tags

Named activities and trip contexts; editable day associations.

Collections & fields

Book / Food schemas, typed properties, options, defaults.

Items & values

Naruto volume 1, status, author, links, collection field values.

Dated history

Individual purchases, consumption, and status changes.

Purchases

Amount, currency, purchase date, spending category, missing details.

Tasks & events

Due dates versus start/end times, with source provenance.

Links & jobs

Cross-context relationships, source result links, summary jobs.

Source → extracted resultsOne source may create several purchases, tasks, events, and item updates. Each result can be traced back to its source.
Collection → fields → item valuesField definitions belong to a collection. An item’s value must match that definition’s type and allowed options.
Item → many history records → optional purchase detailsA food item can appear in many meals. A meal and its payment can share one history identity rather than becoming duplicate search results.
Journal day ↔ activity tags ↔ linked Library historyMany days can share a trip tag. Explicit links let the trip page collect relevant Library records.

Proposed integrity rules

Save the source and selected results atomically with an idempotency key, so retrying Save does not duplicate purchases. Apply owner-based RLS to every user table and validate link ownership. Index owner/date, item/history, and searchable text. Store money exactly; use THB as an initial configurable default, and do not add unlike currencies together without a defined conversion policy.

Primary collection per item is the proposed starting model; collection/category/filter naming and cross-collection behavior are listed as implementation details to validate below.

10 · Delivery sequence

Build one useful loop at a time.

The target first version includes the agreed Library flexibility. These stages are an implementation order, not a proposal to drop that scope. No delivery dates have been estimated.

1

Reliable capture → saved source

Connect actual streaming, readiness/finalization, errors, editable text, journal date, and source persistence. Reconcile the existing source schema.

Exit: a real iPhone recording saves the reviewed text; server failure leaves no recording draft.

2

Selected results → today’s plan

Generate validated cards; save selected tasks, events, purchases, and item links. Implement Home priorities and later editing.

Exit: one spoken mixed example produces correct linked records without duplicate saves.

3

Configurable Library → useful search

Build collection fields/defaults, item pages, wishlist and status updates, dated history, filters/counts, and Budget totals.

Exit: answer “already own?”, “unread books?”, and “junk food this week?” using real saved data.

4

Daily summaries → activity history

Add scheduled/manual summaries, activity tags, explicit named-tag creation, trip links, corrections, and safe regeneration.

Exit: 21:00 generates the day; a later save updates it while preserving user tag corrections.

5

Use it on your phone

Validate thumb reach, misleading extractions, mixed-date speech, missing details, server restarts, and the effort required to maintain the Library.

Suggested evaluation: use it for seven days, then review missed captures, correction effort, and successful lookups. These are evaluation ideas, not agreed numeric targets.

11 · Ready for implementation planning

What a working first version must prove.

  1. Record a mixed sentence and save its selected results without editing cards during capture.
  2. Backdate a journal record without shifting the meaning of “tomorrow” in spoken instructions.
  3. Turn an untimed action into a task and a timed appointment into a one-hour event.
  4. Save a purchase with no price; find its missing details on Home.
  5. Create a newly purchased Book with the configured Unread default.
  6. Find the same book through its fields and purchase history.
  7. Create a wishlist item without increasing spending.
  8. Update an existing item’s reading status without duplicating it.
  9. Find all matching katsudon records this week and display their exact count.
  10. Count expenses once even when Library filters overlap.
  11. Create an explicitly named trip tag and link relevant days and purchases.
  12. Generate a summary at 21:00 and manually; preserve activity-tag corrections on update.
  13. Stop safely on recording failure, retaining no partial recording draft.
  14. Reach capture, save, and common actions comfortably with the left thumb.
Details to validate during implementation

These do not block reading or using this product plan. They remain proposals rather than silently settled decisions.

  • Collection membership: start with one primary configurable collection per item plus flexible labels; validate whether an item needs schemas from several collections.
  • Date semantics: confirm the proposed selected-journal-date default for purchases, date-range UI, and Monday-start weeks.
  • Schema edits: define field deletion, type changes, and how existing values remain recoverable.
  • Deletion: decide whether deleting a source removes or only unlinks its tasks, purchases, and item history.
  • Matching: define duplicate-item resolution, ambiguous times, and what happens when a structured extraction cannot be confidently applied.
  • Saving failures: distinguish failed recording (discard) from post-recording classification/save errors; proposed behavior keeps review text in memory for retry, without a persistent draft.
  • Deployment: verify secure domain access, Supabase reachability, authenticated ownership checks, and server job recovery.

This document describes the planned product. It does not deploy services, change schemas, or claim that the illustrated features are already implemented.
